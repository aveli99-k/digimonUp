# digimonUp 내부 동작 노트

이 문서는 **왜 이렇게 만들었는지**를 남긴 개발 노트입니다.
매크로를 쓰기만 할 때는 읽지 않아도 됩니다 ([README](../README.md) 로 충분합니다).

인식·경로 알고리즘의 세부와, 실제 게임에 붙여 보고서야 알게 된 것들이
전부 실측값과 함께 적혀 있습니다. 코드를 고치기 전에 읽어주세요.
같은 함정을 다시 밟지 않으려고 회귀 테스트로도 남겨두었습니다.

---

## 2번 기능(탐사) 동작

### 창 고정

게임 화면은 계속 바뀌므로 **창 제목만 믿지 않습니다.** 두 조건을 함께 확인합니다.

1. 상단에 고정된 게임 탭 이미지가 있는가 (템플릿을 넣어둔 경우에만 검사)
2. 화면 안에 5x5 게임판 격자 테두리가 있는가

조건을 만족한 창의 HWND 를 고정하고, **실행 중에는 절대 다른 창으로 바꾸지 않습니다.**

앱플레이어의 창 구조는 대체로 이렇습니다 (MuMuPlayer 12 실측).

```
Qt5156QWindowIcon  "Android Device"      <- 최상위 창
  +- Qt5156QWindowIcon  "MuMuNxDevice"
  +- nemuwin           "nemudisplay"     <- 안드로이드 화면이 그려지는 자식 창 (캡처/클릭 대상)
Qt5156QWindowIcon  "MuMuPlayer"          <- 멀티 인스턴스 관리창 (게임 아님, 후보에서 제외)
  +- MuMuNativeWindow "MuMuThumbnailWindow"
```

게임 화면은 `nemudisplay` 자식 창에만 그려지므로 그 창의 **클라이언트 영역만** 캡처합니다.
상단 툴바(키보드/음량/뒤로가기)가 안 들어와서 좌표 계산이 깔끔합니다.

캡처는 `PrintWindow` + `PW_RENDERFULLCONTENT` 를 씁니다. 창이 다른 창에 가려져 있어도
내용을 받아올 수 있고, 전체 모니터를 찍지 않으므로 **창이 이동해도 좌표 기준이 흔들리지 않습니다.**

> 디스플레이 배율(125% 등)이 켜져 있으면 좌표가 어긋납니다. 프로그램은 시작하자마자
> DPI 인식을 켭니다. (실측: 125% 배율에서 창 폭이 567px 로 보고되지만 실제 캡처는 709px)

### 게임판 검출

격자선은 밝기 경계가 **아니라** 채도가 잠깐 내려앉는 1~2px 선입니다.

| | H | S | V |
|---|---|---|---|
| 빈칸 | 101 | 245 | 100 |
| 이동 가능 강조칸 | 102 | 241 | 203 |
| **격자선** | 100 | **171** | 112 |
| 장애물(연보라 피라미드) | 116 | 110 | 134 |

그래서 흑백 Sobel 로는 도시 배경과 UI 글자에 묻힙니다. 대신

1. 게임판 색(H 93~112) 픽셀만 남기고
2. 채도 채널에 black-hat 을 걸어 가늘고 어두운 선만 뽑은 뒤
3. 등간격 6줄 모델 후보를 여러 개 만들고
4. 각 후보를 **선 위 에너지 / 셀 내부에 선이 없는지 / 셀 내부가 실제 게임판 색인지 /
   게임판 실제 범위와 겹치는지** 로 채점해 가장 좋은 것을 고릅니다.
5. 마지막으로 원근 때문에 아래로 갈수록 간격이 줄어드는 것을 따라가도록 각 선을
   실제 검출 피크에 스냅합니다.

고정 비율은 쓰지 않습니다. **검출한 격자선 좌표가 항상 우선입니다.**

> 게임판 위쪽에는 장식용 청록 블록 띠가 있어서, 안쪽 격자선 4개만 보고 맞추면
> '한 칸 위로 밀린' 배치도 점수가 비슷해집니다. 실제로 같은 화면에서 서로 다른 격자가
> 나온 적이 있어, 채도가 더 높은(S≥210) 엄격한 셀 색 마스크로 게임판의 실제 위아래 끝을
> 재서 위상을 고정했습니다. 회귀 테스트로 남겨두었습니다.

검출 결과에는 게임판 bbox, 세로 격자선 6개, 가로 격자선 6개, 각 셀의 Rect 와 중심점,
검출 신뢰도가 들어 있습니다.

### 셀 상태 인식

**위치 기준점은 스프라이트의 질량중심**이다. 처음에는 발끝에서 셀 높이의 20% 를 올린
지점을 썼는데, 옆 칸 아이템 카드가 실루엣 덩어리에 붙어 상자 아래끝이 17px 내려가는
바람에 (1,1) 에 있는 플레이어를 (2,1) 로 읽었다. 그러면 매크로가 **자기 발밑 칸을
클릭**하게 되고, 게임은 당연히 "해당 위치로 이동할 수 없습니다"만 띄운다.
스프라이트의 무게중심은 자기 칸 중앙에 놓이므로(실측: 셀 중심과 2~3px 차이)
가장자리 오염에 훨씬 강하다.

템플릿은 '이게 플레이어가 맞다'를 확인하고 신뢰도를 주는 역할이고, **위치는 항상
이번 프레임의 실루엣**을 기준으로 잡는다. 템플릿을 셀 높이에 맞춰 정규화하는 과정에서
상자가 몇 px 씩 어긋나기 때문이다.


템플릿이 있으면 템플릿 매칭(여러 장 · 좌우 반전 · 여러 배율)을 먼저 쓰고,
없거나 실패하면 색 기반으로 판정합니다. **템플릿이 하나도 없어도 동작합니다.**

플레이어는 애니메이션으로 계속 움직이고 좌우로 뒤집히므로 다음을 지원합니다.

- 여러 플레이어 템플릿 / 좌우 반전 / 여러 크기
- 애니메이션으로 위치가 조금 달라지는 경우
- 발이 다음 셀까지 튀어나오는 경우
- 맨 아래 행에서 하단 테두리에 발이 가려지는 경우
- 바로 위 장애물에 머리나 날개가 가려지는 경우

전체 템플릿 인식이 실패했을 때**만** 머리와 발을 뺀 몸통 중앙으로 보조 인식합니다
(오탐을 줄이기 위해 2순위로 둡니다).

**위치 기준점**: 발끝을 그대로 쓰지 않고 셀 높이의 20% 만큼 위를 논리적 기준점으로 씁니다.
발이 셀 경계를 넘어가도 논리 위치가 흔들리지 않습니다.

**보조 검증**: 게임이 플레이어의 상하좌우를 밝게 표시해 주므로, 그 강조칸 십자의 공통
이웃으로 플레이어 칸을 역산해 교차 검증합니다. 애니메이션과 무관해서 아주 안정적입니다.

**장애물**: 피라미드는 위 셀로 삐져나옵니다. 실측하면 진짜 장애물 셀은 0.72~0.75,
꼭대기만 걸친 위 셀은 0.10~0.11 이라 그 사이(0.32)를 기준으로 가릅니다.

**목적지**: 템플릿이 테두리나 캐릭터에 가려 실패하면 주황색 카드 색상 영역 검출을
보조 수단으로 씁니다. 다만 **목적지 템플릿이 아예 없을 때는 기본적으로 주황색을
목적지로 보지 않습니다.** 일반 아이템도 주황 카드라서 구분할 수 없고, 엉뚱한 칸을
목적지로 삼으면 경로 전체가 틀어지기 때문입니다. 이 경우 목적지 미인식으로 두고
'오른쪽 끝 열' 규칙으로 진행합니다. (`orange_goal_without_template` 로 바꿀 수 있음)

### 경로 계산

1. **주황칩(필수 아이템)** 까지 장애물 없는 최단 경로 — 판에 칩이 여러 개면
   **가장 가까운 것부터**. (매번 '가장 진한 칩'을 고르면 프레임마다 목표가 바뀌어
   제자리를 오간다. 실측으로 한 판에 칩이 2개 놓이는 것을 확인했다.)
2. 목적지가 인식되지 않으면 **오른쪽 끝 열까지 가는 장애물 없는 최단 경로**
3. 오른쪽 끝 열까지 갈 수 있는 장애물 없는 경로가 **전혀 없을 때만** 가장 가까운 장애물 클릭

BFS 가 상하좌우를 모두 훑으므로, 오른쪽으로 바로 못 가더라도 위나 아래로 우회할 수
있으면 반드시 찾아냅니다. **우회할 수 있으면 장애물을 부수지 않습니다.**

3개 연속 장애물 특수 조건은 **가로 방향 XXX 배열에만** 적용합니다. 가운데를 부술 수
있으면 가운데를, 가운데에 닿을 수 없으면 같은 줄의 닿는 칸을 우선합니다.
세로 3개는 특수 조건으로 처리하지 않습니다.

> 참고: 요구사항에 "가로 XXX 특수 조건"이라고만 적혀 있고 조건의 내용이 없어서,
> **가장 크게 뚫리는 가운데를 우선한다**로 해석했습니다. 다른 의도였다면
> `pathfind.py` 의 우선순위 부분만 고치면 됩니다.

#### 장애물 파괴에 대한 실측 결과 (중요)

실제 게임에서 확인해 보니, **장애물(피라미드)을 클릭해도 부서지지 않고
'해당 위치로 이동할 수 없습니다' 안내만 뜹니다.** 인접한 장애물을 눌러도 같았습니다.
같은 자리를 무한히 다시 누르는 일이 없도록 이렇게 막아 두었습니다.

- 파괴 클릭 뒤에 안내문이 뜨면 **실패**로 세고,
- `obstacle_break_max_failures`(기본 2)회 연속 실패하면 **파괴 시도를 아예 접고**,
- 그 뒤로는 길이 열릴 때까지 `blocked_wait_sec`(기본 2초) 간격으로 다시 봅니다.
- 이동에 한 번이라도 성공하면 실패 횟수는 초기화됩니다.
- `allow_obstacle_break: false` 로 처음부터 끌 수도 있습니다.

오른쪽이 막히면 **우측 하단 초록색 버튼**을 눌러 장애물을 부순다. 이 버튼은 사용
횟수가 정해져 있으므로(실측: 30회, 누를 때마다 1씩 줄어드는 것을 확인) 정말 갈 길이
없을 때만 누른다. `green_button_max_uses` 로 한 판당 상한을 둘 수 있다(0 = 제한 없음).

### 이동 입력

방향키가 아니라 마우스 클릭입니다. 현재 플레이어 셀 기준으로 **다음 한 칸의 셀 중심**을
클릭합니다.

```
현재 위치: row=2, col=1
이동 방향: RIGHT
클릭 위치: row=2, col=2 셀 중심
```

클릭 좌표는 반드시 고정된 HWND 의 클라이언트 좌표로 계산한 뒤 `ClientToScreen` 으로
화면 좌표로 바꿉니다. **화면 중앙이나 게임판 중앙을 고정적으로 클릭하지 않습니다.**
클릭 직전에 HWND 유효성을 확인하고 창 포커스를 재시도합니다.

> **다중 모니터 주의.** `SendInput` 의 `MOUSEEVENTF_ABSOLUTE` 는 좌표를 **주 모니터**
> 기준으로 해석합니다. `MOUSEEVENTF_VIRTUALDESK` 를 함께 주지 않으면 보조 모니터에
> 있는 창을 클릭할 때 엉뚱한 곳으로 갑니다. (실측: y=636 을 의도했는데 커서가 y=301 로
> 갔습니다. 주 모니터 높이 1440 / 가상 데스크톱 높이 3040 의 비율만큼 어긋난 것)
> 지금은 두 플래그를 함께 주고, **클릭 직전에 커서가 실제로 그 자리에 갔는지 확인**한 뒤
> 어긋나면 클릭하지 않습니다.

### 빠른 연속 이동

매 한 칸마다 전부 다시 인식하면 느리므로:

```
전체 화면 인식 -> 전체 경로 계산 -> 첫 한 칸 클릭 -> 화면 변화 확인
  -> 안정될 때까지 대기 -> 플레이어 위치만 가볍게 재추적
  -> 예상 칸 도착 확인되면 다음 한 칸 클릭 -> ... -> 경로 끝나면 전체 재인식
```

매 이동 후 전체 객체 인식은 건너뛰되 **격자선은 가볍게 다시 검출**해서 다음 클릭의
셀 중심 좌표를 갱신합니다. 창이 움직여도 어긋나지 않습니다.

### 애니메이션 잔상 방지

연속 좌우 이동에서 이전 칸에 남은 잔상을 이동 성공으로 판단하면 안 됩니다.

- 예상 칸이 **2회 연속** 확인된 뒤에만 다음 클릭을 실행합니다.
- 이전 칸에서 다시 검출되면 성공으로 처리하지 않습니다.
- 게임판이 스크롤하면서 플레이어가 화면상 같은 칸에 남는 경우를 함께 확인합니다.

실측해 보니 **네 방향 모두** 스크롤이 일어납니다. 오른쪽으로 이동하면 게임판이
왼쪽으로 한 열 밀리고 플레이어는 화면상 같은 칸에 그대로 있습니다. 즉
`이동 후[r][c] == 이동 전[r+dr][c+dc]` (dr, dc = 이동 방향) 이 됩니다.

> 처음에는 위상 상관(phase correlation)으로 픽셀 이동량을 쟀는데, 게임판이 108px 주기로
> 반복되는 격자라 상관 피크가 주기 구조에 걸려 0 으로 잡히는 일이 있었습니다.
> 그래서 픽셀 대신 **셀 25칸의 내용 요약(장애물 비율 + 평균 밝기)이 한 칸 밀렸는지**를
> 봅니다. '한 칸 밀림'이 '그대로'보다 뚜렷하게 잘 맞아야 성공으로 인정합니다.
> 이동 가능 강조칸은 판과 함께 스크롤하지 않고 늘 플레이어 주위에 표시되므로 비교에서 뺍니다.
> (그 결과 판정 격차가 0.001 대 0.11 로 벌어집니다)

### 이동 불가 안내 처리

"해당 위치로 이동할 수 없습니다"는 OK 버튼이 있는 모달이 아니라 잠시 뒤 저절로
사라지는 알림입니다. **이 안내문 중앙을 클릭하면 안 됩니다.** 안내가 사라지는 순간
그 클릭이 게임판으로 전달돼 같은 오류가 반복됩니다.

```
안내 감지 -> 모든 마우스 입력 중지 -> 안내문을 클릭하지 않음
  -> 안내가 사라진 화면을 2회 연속 확인 -> 기존 고속 경로 폐기
  -> 전체 화면 재인식 -> 새 경로 계산
```

### 정지

정지 버튼 또는 **중지 키(기본 `F12`)** 를 누르면 다음을 **즉시** 차단합니다.

중지 키는 `GetAsyncKeyState` 로 보므로 창 포커스와 무관하게 어디서 눌러도 먹습니다.
매크로가 마우스를 계속 움직이는 중에는 GUI 의 정지 버튼을 겨냥해서 누르기가
까다롭기 때문에 넣었습니다. 클릭 직전마다 확인하는 자리(`_check_stop`)에서 함께
보므로 반응이 즉각적이고, 한 번 감지하면 `stop_event` 를 세워 두므로 키에서 손을
떼도 계속 정지 상태입니다(GUI 와 같은 깃발을 봅니다).

- 진행 중이던 분석 결과 적용
- 새 경로 시작 / 다음 칸 클릭 / 팝업이나 안내문 클릭 / 자동 재시작

분석 도중 정지 요청이 들어오면, 분석이 끝난 뒤 경로 실행에 들어가기 직전에 다시
확인하므로 **이전 경로가 뒤늦게 실행되지 않습니다.**

## 템플릿 넣기 (선택)

**이미 20장이 들어 있습니다.** (player 6, player_body 6, obstacle 4, item 1,
blocked_toast 3 — 실제 게임 화면에서 잘라 만든 것)

캐릭터가 진화하면 생김새가 바뀌므로 `player` 템플릿은 언젠가 안 맞게 됩니다.
그때는 아래 도구로 다시 찍으면 됩니다. (강조칸 십자로 위치를 역산하는 보조 인식은
외형과 무관하게 계속 동작하므로, 템플릿이 낡아도 완전히 멈추지는 않습니다.)

템플릿이 하나도 없어도 색 기반 인식으로 동작하지만, 넣으면 정확도가 올라갑니다.

```bash
python tools\capture_explore.py
```

`templates/explore/<종류>/` 에 저장되고, 같은 종류에 **여러 장** 넣어도 됩니다
(폴더의 PNG 를 전부 불러서 모두 시도합니다).

| 폴더 | 넣을 것 | 효과 |
|---|---|---|
| `player/` | 플레이어 여러 자세 | 플레이어 인식 정확도 ↑ |
| `player_body/` | 머리·발 뺀 몸통 중앙 | 가려졌을 때 보조 인식 |
| `goal/` | 주황칩 카드의 **중심**(번개 무늬) | 칩 추적 (넣어 두었음) |
| `obstacle/` | 장애물 | 장애물 오탐 ↓ |
| `item/` | 판 위의 걸음수/부수기/돌진 아이템 | 가는 길에 주워 간다 |
| `top_tab/` | 상단 고정 게임 탭 | 창 선택 조건 강화 (안 써도 무방) |
| `blocked_toast/` | "이동할 수 없습니다" 안내문 | **안내문 감지 활성화** |

`goal/` 에는 **칩 카드 전체가 아니라 중심(번개 무늬)** 을 넣습니다. 맨 아래 행에서
게임판 하단 테두리가 카드 아래쪽을 가리기 때문입니다(자세한 이유와 실측은 아래
'주황칩은 색이 아니라 카드 중심 템플릿으로 찾는다' 참고).

템플릿이 없어도 색으로 찾지만, 색 기준(주황 비율 0.035)은 디지몬의 주황 갈기와
경계가 흐릿합니다. 템플릿을 넣으면 점수 0.95 대 기준 0.62 로 여유가 커집니다.

## 실제 게임에서 확인한 것들 (중요)

코드만 보고는 알 수 없고, 실제로 클릭해 보고서야 드러난 것들이다. 전부 회귀 테스트로 남겼다.

### 1. 다중 모니터에서 클릭이 엉뚱한 곳으로 갔다

`SendInput` 의 `MOUSEEVENTF_ABSOLUTE` 는 좌표를 **주 모니터** 기준으로 해석한다.
`MOUSEEVENTF_VIRTUALDESK` 를 함께 주지 않으면 보조 모니터의 창을 클릭할 때 어긋난다.
실측: y=636 을 의도했는데 커서가 y=301 로 갔다(주 모니터 1440 / 가상 데스크톱 3040 비율).
지금은 두 플래그를 함께 주고, **클릭 직전에 커서가 실제로 그 자리에 갔는지 확인**한다.

### 2. 이동 확인이 전부 실패했다 — 추적이 너무 느려서

이동 확인 루프에서 템플릿 매칭을 돌렸더니 **한 번에 1~2초**가 걸렸다.
`move_timeout_sec` 이 2.2초라 '연속 2회 확인'이 물리적으로 불가능했다.
지금은 확인 루프에서 플레이어 추적에 템플릿을 쓰지 않는다(`track_player_fast`, **1.4ms**).
전체 인식(사이클당 1회)만 템플릿을 쓰고, 그것도 실루엣 주변만 훑어 1022ms → 166ms.

다만 이걸로 끝이 아니었다. 아래 9번을 함께 보라 — 플레이어 추적을 아무리 줄여도
**같은 루프 안의 안내문 검사**가 346ms 를 먹고 있어서 확인 기회가 여전히 모자랐다.

### 3. 격자 위상이 매 사이클 한 칸씩 흔들렸다

진짜 배치(conf 0.780)와 한 칸 밀린 가짜 배치(conf 0.779)의 점수 차가 0.001 이라
사실상 동전 던지기였다. 매 사이클 다른 칸을 클릭하니 당연히 아무것도 되지 않았다.
두 가지로 잡았다.

- 가짜 쪽은 마지막 선이 창 가장자리에 달라붙고(xs[-1]=708, 폭 709) 마지막 간격만
  93px 로 좁아진다 → 점수를 매기기 전에 구조로 걸러낸다(`_plausible`).
- 게임판 가로 범위를 잴 때 화면 전체 높이로 나누면 플레이어가 걸친 열 하나 때문에
  구간이 끊긴다 → **세로 범위를 먼저 구하고 그 행들 안에서만** 가로를 잰다.

고친 뒤 12회 연속 캡처에서 격자가 100% 동일했다(전에는 약 50:50 으로 흔들렸다).

### 4. 장애물은 클릭해도 부서지지 않는다

인접한 장애물을 눌러도 매번 "해당 위치로 이동할 수 없습니다"만 떴다.
그래서 `allow_obstacle_break` 기본값은 **false** 다. 켜더라도 연속 실패하면 스스로 접는다.

### 5. 오른쪽 끝 열만 목표로 삼으면 안 된다

한 칸만 가도 새 열이 들어오므로, 지금 보이는 5x5 안에서 맨 오른쪽 열에 못 닿아도
막힌 게 아니다. 목표는 **도달 가능한 가장 오른쪽 칸**이다.

### 6. 막힌 주머니에서는 제자리를 맴돈다

사방이 막힌 5칸짜리 구역에 갇힌 채 25번을 움직였는데 판이 그대로였다.
이동 횟수만 축내므로, **장애물 배치가 3사이클 연속 그대로면** 갇힌 것으로 보고
움직임을 멈추고 기다린다.

### 7. 격자 위상이 계속 흔들려 엉뚱한 곳을 클릭했다

한 칸 밀린 배치와 진짜 배치의 점수 차가 0.001 이라, 매 사이클 격자가 왔다 갔다 하면서
셀 중심이 88px(한 행)씩 튀었다. 그 바람에 주황칩이 두 칸에 걸쳐 인식되지 않고
상하좌우가 아닌 엉뚱한 곳을 클릭했다. 세 겹으로 잡았다.

1. **가장자리 정렬**(`_edge_alignment`) — 게임판 위 끝은 엄격한 셀 색 마스크로 정확히
   잡힌다(y=420). 맞는 배치는 419 에서 시작하고 밀린 배치는 332 에서 시작하므로 확실히 갈린다.
   장애물이 많아 색 구간이 중간에 끊겨도, 양 끝 중 한쪽은 대체로 정확하다.
2. **구조 필터**(`_plausible`) — 창 가장자리에 달라붙거나 마지막 간격만 좁아진 배치를 제외.
3. **다수결 고정**(`_stable_grid`) — 게임판 패널은 화면에서 움직이지 않으므로, 최근
   9프레임의 최빈 배치를 쓴다. 한 장만 보고 고정했더니 그 한 장이 틀렸을 때 계속
   틀린 채로 굳어서, 다수결로 바꿨다.

### 8. 스크롤한 뒤 남은 경로를 그대로 쓰면 안 된다

판이 밀리면 플레이어는 화면상 제자리이고 칸 번호가 통째로 어긋난다. 미리 계산한 경로를
이어서 클릭했더니 두 칸 떨어진 곳을 눌러 "이동할 수 없습니다"가 반복됐다.
지금은 스크롤이 감지되면 남은 경로를 버리고 다시 인식한다.

### 9. 진짜 병목은 플레이어 추적이 아니라 '안내문 검사'였다

2번에서 플레이어 추적을 1~2초에서 1.4ms 로 줄였는데도 이동 확인이 빠듯했다.
확인 루프 한 바퀴를 함수별로 재 보니 범인이 따로 있었다.

| 확인 루프 한 바퀴 | 전 | 후 |
|---|---|---|
| `find_blocked_toast` (안내문 검사) | **346ms** | 62ms |
| `detect_board` (격자 재검출) | 23ms | 11ms |
| `_track_player` (플레이어 추적) | 3.1ms | 1.4ms |
| `_cell_signature` (스크롤 판정) | 11.7ms | 2.9ms |
| **합계** | **385ms** | **78ms** |

안내문 템플릿은 478x77 인데 이걸 709x1260 화면 전체에서 배율 3개 x 템플릿 3장으로
훑고 있었다. 그래서 2.2초 안에 확인 기회가 **5~6번**밖에 없었고, 그중 2번을 연속으로
맞춰야 이동 성공이었다. 한 번만 어긋나도 실패로 잡히는 구조였다.

고친 방법은 **2단계 매칭**(`recognize.match_big`)이다.

1. 화면과 템플릿을 함께 1/3 로 줄여 대충 어디인지 찾는다 (약 1/9 비용)
2. 그 자리 주변만 원본 해상도로 다시 맞춰 **정확한 점수**를 낸다

점수를 결국 원본 해상도에서 재기 때문에 `toast_min` 같은 판정 기준은 그대로 쓴다.
근거는 실측이다. 실제 캡처 **102장**에서 1/3 축소 점수를 재 보니

- 안내문이 있는 프레임: 0.882 ~ 0.953
- 안내문이 없는 프레임: 0.577 ~ 0.588

로 **0.29 만큼 확실히 갈린다.** 축소본이 봉우리를 엉뚱한 데로 옮기지 않는다는 뜻이다.

이제 2.2초 안에 확인 기회가 **약 15~28번** 생긴다. 같은 `confirm_repeat=2` 규칙이
훨씬 여유 있게 만족된다.

곁들여 정리한 것들 (전부 결과값은 그대로다)

- 마스크가 채널을 `int16` 으로 넓혀 비교하고 있었다. 임계값이 전부 0~255 안이라
  넓힐 이유가 없었고, 프레임마다 5MB 짜리 임시 배열이 세 개씩 생겼다 → `cv2.inRange`.
- 같은 프레임의 HSV 를 마스크마다 다시 변환했다(`analyze` 한 번에 7회) → 한 번만.
- 템플릿 리사이즈를 셀 25칸마다 똑같이 반복했다(`analyze` 한 번에 414회) → `TemplateSet` 캐시.
- 스크롤 판정에서 **변하지 않는** 클릭 직전 사진의 셀 요약을 폴링마다 다시 계산했다 → 1회.
- 장애물 템플릿 매칭을 색만으로 이미 판정이 끝난 칸에서도 돌렸다 → 갈리는 칸에서만.

이 정리가 인식 결과를 바꾸지 않았다는 것은 실제 캡처 51장에 대해 격자 좌표/신뢰도,
25칸 분류, 플레이어 칸, 마스크 픽셀 수, 안내문 점수를 최적화 전후로 비교해
**전부 동일**함을 확인했다.

### 10. 격자 위상 밀림이 아직 남아 있었다 — 표가 아니라 신뢰도로 골라야 한다

3번과 7번에서 격자 위상 문제를 잡았다고 적었는데, **실제 MuMuPlayer 로 다시 재보니
아직 남아 있었다.** 같은 화면을 40번 찍었더니 3번(7.5%)이 한 칸 아래로 밀렸다.

```
정상 37회:  y0=419  ->  플레이어 (3,1)  ->  경로: 오른쪽 전진
밀림  3회:  y0=507  ->  플레이어 (4,2)  ->  경로: 위/왼쪽 (완전히 반대 방향)
```

밀린 프레임을 저장해서 보니 **격자선이 거의 사라진 화면**이었다. `PrintWindow` 가
게임이 다시 그리는 도중을 잡은 것이다. 격자선이 약하니 한 칸 밀린 배치가 이긴다.

`_stable_grid` 의 다수결이 이걸 걸러 주기는 했다(37:3). 하지만 두 가지 구멍이 있었다.

**구멍 1: 시작 직후에는 표가 한 장뿐이다.**
`run()` 은 첫 프레임으로 격자를 고정하고 곧바로 경로를 짜서 클릭한다. 그 한 장이
하필 밀린 프레임이면 엉뚱한 칸을 누른다. 그래서 처음 고정할 때는 몇 장을 더 모은다
(`grid_min_votes`). 단, **이동 확인 루프에서는 이 시딩을 하지 않는다.** 거기는
폴링마다 도는 자리라 캡처를 더 하면 확인 기회가 줄어 손해다.

**구멍 2: 다수결로는 안 걸러진다.**
밀린 프레임은 **무리 지어** 들어온다(실측: 40장 중 14, 15, 17번). 그래서 표를 더
모아도 다수결은 나아지지 않는다. 실측 60프레임으로 모의해 보면:

| 모으는 장수 | 다수결 | 최고 신뢰도 |
|---|---|---|
| 1장 | 6.45% | 7.05% |
| 3장 | 6.58% | 3.48% |
| 5장 | 7.00% | **0.00%** |
| 7장 | 7.32% | **0.00%** |

반면 두 배치의 신뢰도는 **아예 겹치지 않았다.**

| | 신뢰도 범위 | 평균 |
|---|---|---|
| 맞는 배치 (y0=419) | 0.882 ~ 0.911 | 0.904 |
| 밀린 배치 (y0=507) | 0.830 ~ 0.853 | 0.840 |

그래서 표 개수가 아니라 **각 배치에서 가장 잘 나온 프레임의 신뢰도**로 고른다.
'한 장이라도 잘 나온 쪽'을 믿는 것이다. 나쁜 프레임이 아무리 몰려 와도 좋은
프레임 한 장을 이기지 못한다.

고친 뒤 실제 게임에서 **40회 연속 모두 정확한 격자**를 잡았다(전 7.5% 오판).

> 교훈: 노이즈가 시간적으로 몰려서 들어오면 다수결은 무력하다. 이럴 때는
> 표를 세지 말고 **품질 신호가 분리되는지**를 먼저 확인해야 한다.

### 11. 아이템 개수를 읽어서 헛클릭을 없앤다

화면 왼쪽 아래에 남은 아이템이 세 줄로 나온다.

| 아이콘 | 실측값 | 뜻 |
|---|---|---|
| 분홍 발자국 | 1,824 | 걸음수 — 한 칸 움직일 때마다 준다 |
| 노란 발톱 | 234 | 부수기 |
| 초록 돌진 | 27 | 돌진 — 우측 하단 버튼이 이걸 쓴다 |

예전에는 이 숫자를 안 봤다. 그래서 **쓸 게 0개일 때도 두 번은 헛클릭**했다.
장애물을 눌러 보고 → 안내문이 뜨고 → 사라질 때까지 기다리고 → 다시 눌러 보고 →
그제서야 접었다. 개수를 먼저 보면 아예 시도하지 않는다. 걸음수가 0이면 더 움직일
수 없으므로 매크로를 멈춘다(전에는 이동 실패만 쌓였다).

**OCR 라이브러리를 쓰지 않았다.** 배포본이 EXE 하나여야 하는데 OCR 엔진을 넣으면
수십 MB 가 늘고 설치도 까다롭다. 대신 이 게임 글꼴이 고정이라는 점을 이용해
숫자 하나하나를 템플릿으로 맞춘다.

1. 왼쪽 아래에서 **채도 높은 덩어리 세 개**(아이콘)를 찾아 각 줄 위치를 잡는다
   — 좌표를 박지 않으므로 창 크기가 달라져도 따라간다
2. 아이콘 오른쪽의 숫자 띠를 잘라 어두운 픽셀만 남긴다
3. 붙은 덩어리로 글자를 나눈다
4. `templates/counters/0~9.png` 와 맞춘다

글자를 나눌 때 걸린 두 가지 (실측 709x1260 기준)

- **띠를 너무 넓게 자르면** 오른쪽 원형 버튼이 들어온다. 그 큰 덩어리가 '가장 큰
  글자'로 잡혀서 진짜 숫자가 전부 걸러졌다. 폭을 아이콘 3.2배로 제한하고, 글자
  사이 간격이 크게 벌어지면 거기서 끊는다.
- **높이로 거른다.** 숫자 13~14px / 띠 40px = 0.33, 쉼표는 0.15, 버튼 조각은 0.83.
  그래서 0.25~0.60 만 숫자로 본다. 쉼표(`1,824`)가 자연스럽게 빠진다.

실제 화면에서 10회 연속 정확히 읽었다(1824 / 234 / 27, 한 번에 1.3~2.7ms).

> **모르면 막지 않는다.** 숫자 하나라도 자신 없으면 그 줄은 `None`(모름)이고,
> 그때는 예전처럼 '해 보고 판단'한다. 0 이라고 **확실히 읽었을 때만** 시도를 막는다.
> 잘못 읽어서 멀쩡한 기능을 못 쓰게 되는 것이 더 나쁘기 때문이다.
> 같은 이유로 숫자 템플릿이 하나도 없어도 매크로는 그냥 돈다.

### 12. 주황칩은 색이 아니라 '카드 중심' 템플릿으로 찾는다

칩이 걸음수보다 중요하다는 것을 확인한 뒤, 칩 인식을 다시 봤더니 두 군데가 약했다.

**(1) 플레이어 옆 칸의 칩을 통째로 못 봤다**

예전에는 '플레이어 상자와 25% 이상 겹치는 칸'을 검사에서 뺐다. 디지몬의 주황 갈기를
칩으로 세지 않으려는 조치였다. 그런데 실측하면

    플레이어 스프라이트 175x141px  vs  셀 108x88px

이라 **상하좌우 이웃 칸이 30~36% 씩 가려진다**(실측: 위 36%, 왼쪽 31%, 오른쪽 31%).
즉 바로 옆 칸의 칩은 구조적으로 못 봤다.

지금은 칸을 빼지 않고 **스프라이트가 차지한 픽셀만** 마스크에서 뺀다. 갈기는 그대로
걸러지면서 옆 칸의 칩은 보인다. 실측(플레이어 옆 칸의 주황 비율, 마스크 전 -> 후):

| 방향 | 전 | 후 | |
|---|---|---|---|
| 위 | 0.0311 | 0.0000 | 갈기가 지워짐 |
| 왼쪽 | 0.0154 | 0.0034 | 갈기가 지워짐 |
| 오른쪽 | 0.0314 | 0.0312 | 진짜 아이템 색은 남음 |

**(2) 색 비율은 애초에 아슬아슬했다**

칩 판정 기준이 주황 비율 0.035 인데, 실제 칩이 0.03~0.09 사이에서 논다.
디지몬 갈기와도 같은 색이라 경계가 흐릿하다.

그래서 `templates/explore/goal/` 에 **칩 카드의 중심(번개 무늬)** 을 넣었다.
카드 전체가 아니라 중심인 이유는 **맨 아래 행에서 게임판 하단 테두리가 카드
아래쪽을 가리기 때문**이다. 중심만 쓰면 가려져도 그대로 맞는다.

실측 (셀 88px 기준, 아래쪽을 테두리 색으로 덮어 가며)

| 가린 높이 | 템플릿 점수 |
|---|---|
| 0px | 1.000 |
| 20px | 1.000 |
| 30px | 1.000 |
| 40px (셀의 45%) | 0.814 |
| 50px | 0.350 (놓침) |

실제 게임에서 **다른 칩**(템플릿을 뜬 그 칩이 아닌)을 30프레임 연속 0.951 로 잡았다.
기준이 0.62 이므로 여유가 크다. 색 기반(0.035 기준)과는 안정성이 다르다.

칸마다 맞춰 보므로 **칩이 여러 개여도 전부** 찾는다. 예전에는 게임판 전체에서 가장
잘 맞는 하나만 찾아서, 판에 칩이 2개일 때 하나를 놓쳤다.

> 템플릿이 없으면 예전처럼 색으로 찾는다. 즉 **없어도 돌아가고**, 넣으면 정확해진다.

**(3) 곁들여: 색 덩어리 점수에서 크기의 무게를 올렸다**

`_player_blob` 은 '면적 + 따뜻한 색 비율'로 플레이어를 골랐는데, 둘을 1:1 로 더하면
**작지만 새빨간 것이 큰 것을 이긴다.** 주황칩이 딱 그렇다. 칩을 플레이어로 오인하면
위치가 통째로 틀어진다. 지금은 `면적비 + 0.3 x warm` 이다.

| | 면적비 | warm | 예전 점수 | 지금 점수 |
|---|---|---|---|---|
| 실제 플레이어 | 1.37 | 0.17 | 1.54 | 1.42 |
| 실제 칩 | 0.37 | 0.04 | 0.41 | 0.38 |
| 합성 칩(단색 주황) | 0.22 | 1.00 | **1.22 (이김)** | 0.52 |

### 13. 가는 길에 있는 아이템은 주워 간다 (돌아가지는 않는다)

판 위에는 **걸음수 / 부수기 / 돌진** 아이템이 놓여 있고, 밟으면 그냥 얻어진다.
칩이 걸음수보다 중요하므로 아이템을 위해 돌아가면 손해지만, **가는 길에 공짜로
얻어지는 것**까지 버릴 이유는 없다.

**규칙: 거리는 절대 늘리지 않는다.** 같은 길이의 경로가 여럿일 때만 주울 게 많은
쪽을 고른다. 아이템 때문에 돌아가거나 장애물을 부수는 일은 없다.

BFS 에서 이렇게 구현한다. BFS 는 거리가 커지는 순서로 꺼내므로, 어떤 칸을 꺼낼
때쯤이면 그 칸으로 올 수 있는 **같은 거리의 이전 칸이 모두 처리돼 있다.** 그래서
처음 발견할 때뿐 아니라 '같은 거리로 또 닿았을 때'도 비교해서, 주운 게 더 많은
쪽으로 이전 칸을 갈아끼우면 된다.

값어치는 칩 4, 아이템 1 이다. 목표로 가는 길에 다른 칩이 놓여 있으면 그 길로 간다.

#### 걸림돌 1: 아이템이 아예 안 보였다

판 위의 걸음수 아이템(분홍 발자국)이 빈칸으로 인식됐다. 따뜻한 색 비율이 0.0212
인데 기준이 0.10 이었다. 아이콘이 셀에 비해 작아서 색 비율로는 안 잡힌다.

칩과 같이 **템플릿**으로 바꿨다. 그런데 아이템 검사는 템플릿을 `셀 높이 x 0.5` 로
정규화하고 있었는데, 실제 아이콘은 셀 높이의 **0.73**(64px / 88px)이라 너무 작게
줄어 맞을 수가 없었다. 정규화를 빼고 배율만 넓게 준다(`ITEM_SCALES`).

#### 걸림돌 2: 칩이 아이템 폴더에 들어 있었다

`templates/explore/item/item_01.png` 이 사실은 **칩**이었다. 세 캡처 모두에서
(4,3) 의 주황 카드가 그것이고, 칩 템플릿과도 0.94 로 맞는다.

칩이 아이템으로 읽히면 **1순위 목표가 아니라 '지나가다 줍는 것'으로 격하된다.**
칩이 걸음수보다 중요한데 정반대로 동작하는 셈이다. `goal/` 로 옮겼다.

지금 상태

| 폴더 | 들어 있는 것 |
|---|---|
| `goal/` | 칩 중심(번개 무늬), 칩 카드 전체 |
| `item/` | 걸음수(분홍 발자국) |

세 아이템(걸음수·부수기·돌진) 템플릿을 모두 넣었다.

#### 걸림돌 3: 노란 부수기 아이템이 칩으로 잡혔다

판 위의 부수기 아이템(노란 발톱)을 색 기반 대체 경로가 주황 카드로 읽었다
(주황 비율 0.067 -> 칩 판정). 그러면 매크로가 아이템을 **1순위 목표**로 쫓아간다.
칩이 걸음수보다 중요하다는 원칙이 정반대로 작동하는 셈이다. 노란색과 주황색은
색만으로 가르기 어렵다.

그래서 **아이템 템플릿을 칩보다 먼저** 보고, 아이템으로 확인된 칸은 칩 색 판정에서
뺀다. 템플릿이 색보다 강한 증거다. 같은 칸에 둘 다 맞으면 점수가 높은 쪽을 따른다.

#### 걸림돌 4: 기준을 낮게 잡으니 빈칸이 깜빡였다

아이템 템플릿은 아이콘 주변의 발광 고리와 파란 배경을 함께 담고 있어서, 아무
파란 칸에나 0.6 언저리로 맞는다. 기준이 0.60 이었을 때 빈칸 3곳이 아이템으로
잡혔다. 실측하면 갈림이 뚜렷하다.

| | 점수 |
|---|---|
| 진짜 아이템 | 1.000 |
| 나머지 칸 최대 | 0.613 |

기준을 **0.78** 로 올렸다. 20프레임 연속 같은 두 칸만 잡힌다.

또 하나, **아이템 템플릿이 있으면 색 추측은 쓰지 않는다.** 둘을 같이 보면
디지몬 애니메이션의 주황 픽셀이 순간적으로 새어 엉뚱한 칸이 2/15 프레임쯤
깜빡였다. 템플릿이 없을 때만 색으로 찾는다.

### 14. DPI 인식을 안 켜면 모든 것이 조용히 무너진다

디버깅 중에 직접 밟은 함정이다. 진단 스크립트에서 `enable_dpi_awareness()` 를
빼먹었더니 이렇게 됐다.

```
창 크기 보고    709x1260  ->  567x1008   (정확히 80%)
격자            셀 폭 108  ->  53         (반쪽에서 격자를 찾음)
결과            이동 0 / 실패 10, 없는 칩이 보이고, 좌우로 왔다갔다
```

무서운 점은 **화면은 멀쩡해 보인다**는 것이다. 캡처도 되고 격자도 '찾았다'고
나오고 클릭도 나간다. 다만 전부 어긋나 있을 뿐이다. 증상만 보면 인식 알고리즘이
잘못된 것처럼 보여서 한참 엉뚱한 데를 팠다.

그래서 `ExploreEngine.run()` 이 **직접** `enable_dpi_awareness()` 를 부른다.
프로세스마다 한 번만 켜면 되고 여러 번 불러도 문제없으므로, 부르는 쪽
(launcher/gui)이 이미 켰더라도 손해가 없다. 부르는 쪽을 믿지 않는 편이 낫다.

> 증상이 '인식이 이상하다' 일 때 제일 먼저 확인할 것: 캡처한 이미지 크기가
> 창의 실제 픽셀 크기와 같은가. 다르면 DPI 문제다.

### 15. 아이템은 '가는 길'만으로는 부족했다

13번에서 '같은 거리면 아이템을 밟는 쪽'을 골랐는데, 실제로 돌려 보니
**한 칸 옆에 있어도 그냥 지나쳤다.** 전진 경로가 직선이면 옆으로 벗어난
아이템은 영원히 동점 후보가 되지 못하기 때문이다(실측: 2칸·4칸 거리의 아이템
둘 다 못 먹고 지나갔다).

그래서 순위를 하나 넣었다.

1. 주황칩 (거리 제한 없음)
2. **전진 경로에서 벗어나 있는** 근처 아이템 (기본 2칸까지)
3. 오른쪽 전진
4. 세로 이동 / 5. 장애물 파괴

두 가지를 조건으로 달았다.

- **이미 전진 경로 위에 있으면 들르지 않는다.** 어차피 지나가며 먹으므로,
  거기서 멈추면 전진만 손해다.
- **걸음수 아이템은 들르지 않는다.** 걸음수는 이동에 쓰는 자원 그 자체다.
  두 칸 걸어가서 걸음수를 얻으면 본전이거나 손해다. 부수기·돌진은 걸음수로
  살 수 없으니 조금 돌아갈 값어치가 있다. (가는 길에 걸리면 걸음수도 먹는다.)

종류는 템플릿 파일 이름에서 읽는다(`item_steps.png` -> `steps`). 그래서 새
아이템을 추가할 때 파일 이름만 규칙에 맞추면 된다.
